## A recommendation I reversed

UI-2 deferred the reference mockup's bottom tab bar, and UI-10 proposed keeping the drawer
"until there is usage data to decide which five destinations matter". That argument was weaker
than it sounded: **§23 already names the mobile priorities** — quick edits, Tap Profiles,
analytics, NFC, QR, sharing. The charter answered the question I claimed to lack data for.

So the tab bar ships. A drawer costs an extra tap on *every* navigation; a tab bar sits in the
thumb zone and is always visible.

**Home · Profiles · [+] · Insights · More** — with Devices, Customers, Billing and Settings
behind More, which is where a phone user goes rarely. The raised centre control is a real
action (create a link), not decoration: it is the one thing an owner does standing in their
shop. The drawer is kept, demoted from primary mechanism to overflow.

## The gap this sprint found

**`config.seo` had been captured since UI-4 and nothing ever read it.** Every shared profile
previewed as "Hornbill TapTap" — on a product whose entire distribution is people pasting
links into WhatsApp, that is the most visible thing a profile has, and it was our name on
their business.

Now: `generateMetadata` per profile, and a **generated OG image** carrying the business name,
its tagline and **its own accent colour**, so a shared link looks like the business rather
than like our platform. Rendered from the published page only, so an unpublished draft never
leaks through a preview.

A smaller thing found while checking it: with no page to read, the OG fallback used
`DEFAULT_THEME.accent` — `#111827`, a navy that predates the design system and belongs to
neither brand. It now falls back to Hornbill orange.

## PWA

- **Manifest and icons via Next's file conventions**, not a checked-in `public/` directory:
  `app/manifest.ts`, `app/icon.tsx`, `app/apple-icon.tsx`. The icons are generated by
  `next/og` at request time, so the installed icon and the browser-tab favicon are literally
  the same route and cannot drift apart. No binary assets, no image tooling in the build.
- **A separate maskable icon**, because Android crops launcher icons to the device's own shape
  — circle, squircle, teardrop — and the unpadded mark would lose its beak to the crop. Served
  from `/api/icon-maskable` rather than the root, so it cannot occupy a customer-facing name.
- **`viewportFit: "cover"`** plus `env(safe-area-inset-*)` on the tab bar and main region, so
  the layout paints under a notch without controls landing beneath the home indicator.
- `appleWebApp` metadata so an installed instance opens standalone rather than in Safari
  chrome.

### The service worker is deliberately timid

A service worker is the easiest way to ship a bug that survives a deploy — a stale cache can
pin users to an old build with no way to recover. So:

- **Network first** for navigations. The network always wins when available, so a published
  change is never masked by a cached copy.
- **Cache is a fallback only**, for when the network fails. That is the case that actually
  matters here: a customer tapping a card on a weak connection, which in Kenya is an ordinary
  Tuesday rather than an edge case.
- **Nothing authenticated or mutable is ever cached** — no `/api`, `/dashboard`, `/login`,
  `/print`, and GET only.
- **Registration is production-only**, and any worker left by an earlier session is actively
  unregistered in development, so nobody spends an afternoon on a change that "did nothing".

## Honest note on the logo

The hornbill mark is still the inline SVG placeholder written in UI-2. Rendered at icon size
it reads as an abstract orange bird — recognisable, but it is a stand-in, not a brand asset.
If Hornbill has an official mark, replacing `components/shell/logo.tsx` and the three icon
routes is a ten-minute job and will make the installed app look considerably more finished.

## Technical debt

- The service worker caches public pages for offline fallback. Network-first means a stale
  copy only ever appears when genuinely offline, but a page unpublished while a visitor is
  offline could still show from cache until they reconnect. Acceptable; worth knowing.
- No install prompt UI. The browser's own prompt works, but a "add to home screen" nudge at
  the right moment would convert far better. Deliberately not guessed at without usage data.
- No per-profile OG image caching strategy beyond Next's defaults; heavy sharing of one
  profile will regenerate more than it needs to.
- Carried forward: no error/loading boundaries, `force-dynamic` everywhere,
  `middleware`→`proxy` rename pending, **prices still DRAFT**, the builder still unexercised
  by hand, and **physical NFC verification outstanding from UI-6**.

> ⚠ **Migrations `0012` and `0013` remain pending.**

## Next sprint proposal — UI-12: Production polish

The last sprint. Its job is to close what every previous sprint deferred rather than add
anything new:

- **`error.tsx`, `loading.tsx` and `not-found.tsx`** — still absent on every route, so a
  failed query shows Next's default error page and a slow one shows nothing at all. This is
  the largest remaining gap in the product's finish.
- **A branded 404** for an unknown slug — currently a tapped card pointing at a deleted
  profile shows a stock page.
- **The `middleware` → `proxy` rename**, deprecated since Next 16 and deliberately deferred
  because it touches the auth path and deserved its own change.
- An accessibility sweep against the UI-0 findings list to confirm what actually closed, a
  performance pass (`force-dynamic` is on every dashboard route and some of it is cacheable),
  and browser/responsive QA.

Two things I cannot do and that belong in the same window: **physical NFC verification** and
**confirming the plan prices**.
